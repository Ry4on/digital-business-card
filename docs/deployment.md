# Бесплатный стенд: Render + Neon

Инструкция проверена по официальной документации 27 октября 2026 года. В этой схеме приложение размещается на **Render Free**, PostgreSQL — на **Neon Free**. Аккаунты и публикация создаются отдельно; наличие этих файлов ещё не означает, что стенд развёрнут.

## Что входит в бесплатный вариант

Render Free останавливает приложение после 15 минут без входящих запросов; следующий посетитель ждёт пробуждения примерно минуту. Данные остаются в отдельной PostgreSQL, поэтому остановка контейнера их не удаляет. На рабочее пространство выделяется 750 часов бесплатных инстансов в месяц, также действуют лимиты сборок и трафика. [Render Free](https://render.com/docs/free).

Neon Free стоит $0, не ограничен пробным сроком и не требует карты. На проект включены 1 GB хранения и 100 CU-hours вычислений в месяц. Вычислительный узел засыпает после пяти минут бездействия, сохраняя данные. Здесь нет обязательного удаления базы через 30 дней, как у Render Free Postgres. Проверяйте текущие квоты в панели: бесплатный тариф не означает неограниченные ресурсы. [Neon pricing](https://neon.com/pricing).

Платные планы для этой инструкции не нужны. Перед созданием ресурсов убедитесь, что выбран Free и интерфейс не предлагает платный экземпляр. Не подключайте карту для автоматической оплаты превышений: Render описывает возможность дополнительных списаний за трафик и сборки при добавленном способе оплаты. [Render FAQ](https://render.com/docs/faq).

## 1. PostgreSQL в Neon

1. Создайте аккаунт Neon и проект на **Free**. Для этого стенда достаточно одной базы и одной ветки.
2. Выберите регион рядом с Render **Frankfurt**; при доступном выборе версии используйте PostgreSQL 17, на которой проверено приложение.
3. В окне **Connect** выберите нужную базу и роль. Отключите **Connection pooling**, чтобы получить прямой адрес. Его hostname не содержит суффикса `-pooler`.
4. Скопируйте только PostgreSQL URL, без оболочки `psql` и кавычек. Сохраните параметры TLS из Neon, включая `sslmode=require` и `channel_binding=require`, если они присутствуют. Пароль и URL вводятся только в Environment сервиса Render.

Приложение использует стандартное PostgreSQL-подключение через `pg`. Прямой адрес выбран для одного контейнера с небольшим пулом: один `DATABASE_URL` используется и API, и миграциями Prisma при старте. Разделение pooled/direct URL здесь не требуется. Подробнее: [подключение приложения к Neon](https://neon.com/docs/connect/connect-from-any-app), [Prisma и Neon](https://neon.com/docs/guides/prisma).

## 2. Приложение в Render

Сначала опубликуйте этот проект в собственном GitHub-репозитории и дождитесь успешного workflow **CI** на выбранном коммите.

1. В Render подключите GitHub-аккаунт с доступом к репозиторию. Откройте **New → Blueprint**, выберите репозиторий и ветку с `render.yaml`.
2. Проверьте предлагаемый ресурс: один **Web Service**, runtime **Docker**, plan **Free**, регион **Frankfurt**. База Render в Blueprint не создаётся.
3. При запросе `DATABASE_URL` вставьте прямой URL из Neon. В YAML стоит `sync: false`, поэтому Render запрашивает значение при создании Blueprint и не хранит его в репозитории.
4. Примените Blueprint. Render собирает существующий `Dockerfile` и использует его `CMD`: миграции → seed → HTTP-сервер. Отдельные Build Command, Docker Command и Pre-deploy Command задавать не нужно. Приложение слушает `0.0.0.0` и переданный платформой `PORT`.
5. Откройте логи сервиса. После успешных миграций ожидается `Profile initialized.` и запуск Nest. Затем Render проверяет `/health` и переводит сервис в Live.

Параметры `runtime: docker`, `plan: free`, `healthCheckPath` и `sync: false` описаны в [Blueprint reference](https://render.com/docs/blueprint-spec). Использование Dockerfile `CMD` подтверждено в [Docker on Render](https://render.com/docs/docker). Успех `/health` означает, что приложение отвечает и PostgreSQL доступна; Render ожидает успешный HTTP-ответ за пять секунд. [Health Checks](https://render.com/docs/health-checks).

Если Blueprint создаётся для уже существующего сервиса, новый секрет с `sync: false` не запрашивается повторно: обновите `DATABASE_URL` вручную в **Environment**, затем сохраните изменения с развёртыванием.

## 3. Проверка и ссылки для сдачи

Render покажет фактический HTTPS-адрес сервиса. Сохраните две ссылки:

- `https://<фактический-домен>.onrender.com/graphql` — Apollo Sandbox для проверяющего.
- Фактический URL GitHub-репозитория — исходники и README.

Проверьте `/health`: ожидаются `200` и `{"status":"ok"}`. Затем откройте `/graphql` и выполните запрос:

```graphql
query BusinessCard {
  profile {
    name
    description
    links { label url }
    skills { name }
    experience { company position startDate endDate achievements }
    projects { name description url }
  }
}
```

Если в ранее открытой вкладке Sandbox остался другой запрос, замените текст редактора этим примером. После ручного перезапуска сервиса проверьте тот же ответ: миграции и seed повторяются безопасно, дубликаты не добавляются.

Перед демонстрацией откройте ссылку заранее и дождитесь пробуждения Free-сервиса. Сотруднику, который будет проверять задание, можно написать: «Стенд на бесплатном тарифе; первый запуск после простоя занимает около минуты».

## Обновления

В `render.yaml` задано `autoDeployTrigger: checksPass`: после изменений в связанной ветке Render ожидает успешных CI-проверок. Для этого нужен подключённый GitHub-провайдер. Если проверок у коммита нет либо одна завершилась ошибкой, автоматического deployment не будет. Публикация по одному публичному Git URL без интеграции выполняется вручную. [Deploying on Render](https://render.com/docs/deploys).

Изменение TypeScript или `data/profile.json` отправляется обычным коммитом. Новый Docker-образ включает актуальный JSON, а старт контейнера синхронизирует его с Neon. Локальные `.env`, адрес локальной Docker-базы и её пароль для опубликованного сервиса не используются.
