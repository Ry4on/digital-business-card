# Цифровая визитка — Евгений Курбатов

Backend-приложение с публичным GraphQL API: профиль, профессиональные ссылки, навыки, опыт работы и проекты. При старте приложение применяет миграции PostgreSQL и заполняет базу данными из `data/profile.json`.

Стек: TypeScript, Node.js 24, NestJS 12, Prisma 7, PostgreSQL 17, GraphQL, Apollo Server 5, Docker и Git. Версии зависимостей зафиксированы в `pnpm-lock.yaml`; пакетный менеджер — pnpm 11.25.0.

## Запуск с нуля

Нужны Docker Engine / Docker Desktop и Docker Compose v2. Из корня репозитория:

```sh
docker compose up --build --wait
```

После успешного запуска:

- [Apollo Sandbox](http://localhost:3000/graphql) — документация схемы и выполнение запросов.
- [Readiness endpoint](http://localhost:3000/health) — проверка соединения с PostgreSQL.
- Открытие `/` перенаправляет на `/graphql`.

Ручное создание таблиц, выполнение SQL и отдельный запуск seed не нужны. Compose сначала ждёт готовности PostgreSQL. Контейнер приложения применяет миграции, выполняет seed и только после этого начинает слушать порт. Ошибка миграции или заполнения базы останавливает запуск.

Команды управления:

```sh
docker compose logs -f app
docker compose down
docker compose up --build --wait
```

Данные сохраняются в Docker volume между перезапусками. Локальные учётные данные в Compose предназначены для демонстрационной базы. Для публикации используйте отдельную PostgreSQL с собственным паролем.

Если порты заняты, задайте `PORT` и/или `POSTGRES_PORT` в `.env` рядом с `compose.yaml`. `PORT` меняет внешний порт приложения; внутри контейнера остаётся 3000. При изменении `POSTGRES_PORT` для запуска Node.js вне контейнера также исправьте порт в `DATABASE_URL`.

## Пример запроса

Apollo Sandbox открывается с готовым запросом `BusinessCard`. Нажмите кнопку выполнения. Этот же запрос можно вставить вручную, если браузер сохранил старую вкладку:

```graphql
query BusinessCard {
  profile {
    name
    description
    links {
      label
      url
    }
    skills {
      name
    }
    experience {
      company
      position
      startDate
      endDate
      achievements
    }
    projects {
      name
      description
      url
    }
  }
}
```

`endDate: null` обозначает текущую работу. Даты передаются через scalar `DateTime` (`GraphQLISODateTime` из `@nestjs/graphql`); если в исходном резюме известен только месяц, в данных используется первое число этого месяца. Коллекции имеют стабильный порядок, заданный в исходном файле.

API предназначен для чтения. В нём нет мутаций, регистрации и административных операций. Introspection и embedded Apollo Sandbox включены также при `NODE_ENV=production`, чтобы проверяющий мог изучить схему на опубликованном стенде. Для загрузки интерфейса Sandbox нужен доступ браузера к ресурсам Apollo; сам GraphQL API доступен любому HTTP-клиенту.

## Архитектурные решения

```text
GraphQL query
    ↓
ProfileResolver  — транспортный контракт
    ↓
ProfileService   — сценарий получения визитки
    ↓
ProfileRepository — запросы и порядок данных
    ↓
PrismaService → PostgreSQL
```

Выбран один NestJS feature-модуль `ProfileModule`. Объём задачи не требует микросервисов, CQRS или универсальной системы репозиториев. При этом транспорт, бизнес-сценарий и доступ к данным разделены: изменение SQL или Prisma-запроса не требует менять GraphQL resolver.

Используется code-first GraphQL: публичная схема формируется из типизированных DTO. Модели API отделены от Prisma-моделей, поэтому внутренние `profileId` и `sortOrder` не становятся частью публичного контракта автоматически. Prisma-клиент создаётся один раз на приложение и закрывается при завершении работы.

### Вложенные данные и запросы к БД

Профиль загружается через один вызов repository с `include` для четырёх коллекций. Prisma выполняет ограниченное число SQL-запросов: запрос профиля и пакетные запросы связей. Отдельные резолверы не ходят в БД для каждого навыка или проекта, поэтому проблема N+1 не возникает. Число запросов не растёт с количеством элементов коллекций.

Компромисс выбран осознанно: все небольшие коллекции одной визитки загружаются даже тогда, когда клиент запросил только имя. Это проще и надёжнее самостоятельного преобразования GraphQL AST в Prisma `select`, где нужно учитывать fragments, aliases и directives. Для списка большого числа профилей или тяжёлых связей следующим шагом будут выборочная загрузка и/или DataLoader, после измерения нагрузки. GraphQL возвращает клиенту только запрошенные поля.

### Схема данных

`Profile` связан с `ProfessionalLink`, `Skill`, `Experience` и `Project` отношениями один-ко-многим. Внешние ключи поддерживают целостность, индексы по `profileId` и `sortOrder` соответствуют запросам приложения. Уникальные ограничения предотвращают дубли навыков, ссылок и проектов внутри профиля. Достижения хранятся как PostgreSQL `text[]`: у них нет самостоятельной идентичности или отдельного жизненного цикла.

### Подготовка и заполнение базы

Миграции сохранены в Git и применяются командой `prisma migrate deploy`; создание миграций и `db push` не выполняются при запуске. Генерация Prisma Client происходит при сборке.

Seed читает `data/profile.json` и синхронизирует данные профиля атомарно. Повторный запуск не создаёт дубликатов. Этот JSON — источник истины для демонстрационной визитки: изменение файла и новый запуск обновляют опубликованные данные. Ручные изменения принадлежащих профилю записей в БД будут заменены seed при следующем запуске.

До записи JSON проверяется: обязательные поля, HTTP(S)-ссылки, даты и уникальность элементов. Внутри одной транзакции seed берёт PostgreSQL advisory lock, обновляет профиль и заменяет только принадлежащие ему коллекции. Идентификаторы вычисляются из содержательных ключей, поэтому сохраняются между перезапусками и перестановкой элементов. Ошибка записи откатывает весь seed; параллельные процессы заполнения сериализуются.

Публичные данные взяты из резюме и уточнений автора. В проектах указаны открытые репозитории [TRVP](https://github.com/Ry4on/TRVP) и [Gradreserch](https://github.com/Ry4on/Gradreserch). Клиентский код и материалы под NDA не используются.

`GET /health` выполняет запрос к PostgreSQL и возвращает ошибку, если база недоступна. Это проверка готовности обслуживать запросы. Healthcheck контейнера использует тот же endpoint. Образ запускается от непривилегированного пользователя; финальный Node-процесс получает сигналы завершения через `exec`.

## Локальная разработка

Нужны Node.js 24 и pnpm 11.25.0. PostgreSQL можно запустить отдельно через Compose:

```sh
docker compose up -d db
```

Скопируйте `.env.example` в `.env` и установите зависимости:

```sh
pnpm install --frozen-lockfile
pnpm build
pnpm start
```

`pnpm start` применяет миграции, выполняет скомпилированный seed и запускает приложение. После изменения TypeScript-файлов повторите `pnpm build` и `pnpm start`. После изменения `data/profile.json` достаточно перезапуска приложения.

Изменение схемы в разработке:

```sh
pnpm exec prisma migrate dev --name describe_change
pnpm build
pnpm start
```

Новые migration-файлы нужно сохранить в Git. Production запускает уже подготовленные миграции.

## Проверки

```sh
pnpm build
pnpm typecheck
pnpm test
```

Интеграционные тесты используют настоящую PostgreSQL. Для них нужна отдельная, выделенная тестам база: seed изменяет данные профиля в ней.

```sh
# Перед запуском задайте DATABASE_URL и TEST_DATABASE_URL
# одной и той же отдельной тестовой базы.
pnpm db:deploy
pnpm test:integration
```

GitHub Actions устанавливает зависимости по lockfile, собирает приложение, проверяет типы, запускает unit- и integration-тесты с PostgreSQL. Затем workflow собирает Docker-образ, запускает полный Compose-стек с пустым volume и выполняет GraphQL-запрос через HTTP. Это описание настроенного workflow, а не утверждение о результате ещё не выполненного удалённого запуска.

При подготовке решения на Windows и Node.js 24.22.1 выполнены: установка по lockfile, генерация и валидация Prisma, сборка, проверка типов и 8 unit-тестов. Все 7 интеграционных сценариев повторно прошли с PostgreSQL 17.11 из Docker: вложенный HTTP-запрос, Sandbox, порядок коллекций, параллельный seed, синхронизация, откат транзакции и постоянное число SQL-запросов при 100 навыках.

На Docker Desktop 4.97.0 с Linux-контейнерами проверена чистая сборка `docker compose up --build --wait`: новый volume, автоматическая миграция и seed, запуск приложения от пользователя `node` при `NODE_ENV=production`, healthcheck и полный GraphQL-запрос с проверкой всех полей по исходному JSON. После `docker compose down` и повторного `docker compose up --wait` база сохранила историю миграций, данные вернулись без дубликатов, оба контейнера получили статус `healthy`. Временная интеграционная база удалена; основной стенд продолжает работать.

## Развёртывание

Для бесплатного демонстрационного стенда подготовлены `render.yaml` и [инструкция Render Free + Neon Free](docs/deployment.md). Render собирает этот Dockerfile, а адрес Neon задаётся секретной переменной `DATABASE_URL`. После простоя первое открытие бесплатного сервиса может занять около минуты.

Приложение можно развернуть на хостинге, который поддерживает Docker и постоянную PostgreSQL:

1. Создайте PostgreSQL и задайте её адрес в переменной `DATABASE_URL` сервиса приложения. Если провайдер требует TLS, используйте его рекомендованные параметры подключения.
2. Соберите образ из этого `Dockerfile`; дополнительных build-команд и отдельных migration jobs для одного экземпляра приложения не требуется.
3. Передайте `NODE_ENV=production` и `PORT`, если платформа назначает порт сама. Приложение слушает `0.0.0.0`.
4. Настройте healthcheck на `/health` и HTTPS на стороне платформы.
5. Откройте публичный `/graphql` и выполните пример запроса.

Параметры локальной базы из Compose не следует переносить в публичное окружение. Переменные окружения хостинга не сохраняются в репозиторий.

Для сдачи задания нужны две ссылки: публичный `https://<host>/graphql` с Apollo Sandbox и репозиторий с исходным кодом. Локальный адрес `localhost` доступен только на компьютере разработчика. Публикация стенда и репозитория выполняется отдельно после проверки данных визитки.
